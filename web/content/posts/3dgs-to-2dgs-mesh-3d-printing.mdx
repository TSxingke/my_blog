上一篇文章里，我主要记录了怎么在 Ubuntu 上把 3D Gaussian Splatting 跑起来：环境、COLMAP、抽帧、训练命令，还有一些显存相关的小坑。那时的目标很朴素：先生成最原始的3DGS模型。

这篇往后走一步：**能不能把 3DGS 从屏幕里拿出来，变成一个真的能摆在桌上的东西？**

换句话说，我想做的不是再训练一个更漂亮的 viewer 预览，而是把一个自行车的 3DGS 重建结果转成传统 Mesh，修到可以打印，最后真的送去 3D 打印。整个过程大概是：

```text
拍摄数据 -> COLMAP/3DGS -> 2DGS 或 SuGaR -> Mesh -> 修复/减面/补结构 -> 3D 打印
```

听起来像一条很顺的流水线，实际跑下来更像是在几个表示之间来回搬家。3DGS 负责“看起来像”，Mesh 负责“几何上站得住”，3D 打印则负责最后照进现实。

![从 3DGS 预览到 3D 打印实物](/post2/pic1.png)

这次我最后采用的是 **2D Gaussian Splatting（2DGS）** 的 Mesh 化结果，而不是 **SuGaR**。（限于2025年11月之前的算法）

原因不是 2DGS 在所有场景都优于 SuGaR，而是对于我这次的自行车模型来说，2DGS 生成的表面更平整，后续修补和打印适配更顺。SuGaR 我也实际跑过，它的一个明显优点是可以生成带贴图的传统 Mesh 结果，输出里会有 `.obj`、`.mtl` 和贴图图片，对于可视化、Blender 预览、材质表达都更友好。但这次目标不是做一个漂亮的可视化模型，而是做一个**能修、能切片、能打印**的实体模型。

自行车这个对象相对并不是一个非常适合模型化的目标：车架有细管，轮圈有细边，辐条更是又细又多，同时车架的几何流线也非常平滑。只要表面不够平整，或者细结构断裂、粘连、破面，到了打印前处理阶段都会变成工作量。最后我更看重几何稳定性，所以选择了 2DGS。

---

## 从视觉模型到可制造模型

3DGS 很适合做新视角合成。它用一堆可学习的 3D Gaussian 来表达场景，渲染时把这些高斯投影到相机平面上，通过 splatting 合成图像。只要训练得不错，在 viewer 里转一圈会很有“这不就是实物吗”的错觉。

但 3D 打印不吃这一套。打印机不关心你的 viewer 里多像，它需要的是传统几何：

- 表面尽量连续。
- 最好是封闭体，或者至少能被切片软件稳定修复。
- 细结构要有足够厚度。
- 拓扑不能满地碎片、非流形边和自交面。
- 面数不能高到软件打不开，低到结构又全没了。

所以这一步不是“导出一下”那么简单，而是一次从视觉表达向制造表达的转换。

## 2DGS 和 SuGaR：两条路线的取舍

我主要看了两条路线：2DGS 和 SuGaR。

2DGS 的完整名字是 **2D Gaussian Splatting for Geometrically Accurate Radiance Fields**。它不再把场景单纯表示成 3D 空间里的高斯椭球，而是用一组带方向的 2D disks / surfels 来表达表面，并通过法线、深度等正则项提升几何一致性。

直觉上，它比原始 3DGS 更关心“表面在哪里”。这对 Mesh 化很重要，因为最后要提取的是一个面，而不是一堆看起来能合成图像的半透明高斯。

2DGS 仓库里提供了 Mesh extraction。对于边界明确的对象，可以使用 bounded TSDF fusion；对于室外、大场景或者边界不太明确的数据，可以使用 unbounded mesh extraction。我的自行车是在室外拍摄的，且不关注周围形成的封闭空间，所以最后采用的是 `--unbounded`。

SuGaR 的方向也很直接：从已有 3DGS 出发，让高斯更好地和场景表面对齐，然后提取 Mesh。它完整流程里包含 vanilla 3DGS 优化、SuGaR 优化、Mesh extraction、refinement，以及可选的 textured mesh extraction。

我在自行车数据上实际跑过 SuGaR，输出目录里能看到 coarse mesh、refined mesh、refined ply 等结果。它很吸引人的一点是可以生成传统带材质文件的 Mesh，比如 `.obj`、`.mtl` 和贴图图片。这对后续拿到 Blender 里看、编辑、做视觉展示都很方便。

但在这次的自行车模型上，SuGaR 的表面结果没有 2DGS 那么平整。对于只在屏幕上看，它有贴图加持，观感并不差；但到了 3D 打印，贴图不会帮你补几何。打印只认表面、厚度、连通性和支撑关系。这个时候，表面不平整、细结构不稳定的问题就会被放大。

## 2DGS 训练与 Mesh 化

训练环境基本沿用上一篇 3DGS 部署文章中的本机配置。渲染和 Mesh 化阶段我换到了其他机器上，主要是为了扛住内存和显存压力。

| 项目 | 配置 / 说明 |
|------|-------------|
| 训练机器 | 与上一篇 3DGS 部署文章中的本机配置一致 |
| Mesh 化机器 | RTX 3090 + 64GB RAM |
| 2DGS 仓库 | `hbb1/2d-gaussian-splatting` |
| SuGaR 仓库 | `Anttwo/SuGaR` |
| 数据 | 自行车室外拍摄数据，经过 COLMAP 处理 |

这里特别提醒一句：Mesh 化阶段不只是吃显存，也很吃系统内存。尤其是 unbounded mesh extraction 或较高分辨率体素化时，RAM 压力会非常明显。我在渲染过程中还做过一些内存加载相关的代码优化，用来降低峰值内存压力，不过当时没有完整记录具体 patch，所以这里不展开成可复现修改。

2DGS 可以直接使用 COLMAP 格式的数据，可通过原版3DGS生成。我的数据目录在 2DGS 仓库下的 `data/` 里，例如：

```text
data/bike_DJ_4
data/bike_DJ_5
```

训练命令形式如下：

```bash
python train.py \
  -s data/bike_DJ_4 \
  -m output/<run_id>
```

其中：

- `-s` 指向 COLMAP 数据目录。
- `-m` 指向模型输出目录。
- `--lambda_normal` 是法线一致性正则权重。
- `--lambda_distortion` 是深度 distortion 正则权重。
- `--depth_ratio` 控制深度使用方式，`0` 更偏 mean depth，`1` 更偏 median depth。2DGS README 里也提到，对于 unbounded 或 large scenes，`depth_ratio=0` 往往更合适。

我这次没有把文章重点放在训练指标上，因为最终目标不是 novel view synthesis 的 PSNR，而是后面 Mesh 能不能经得住修复和打印。但训练质量仍然会影响 Mesh。一个在 viewer 里已经明显漂、糊、断的 3D/2DGS 结果，后面通常很难靠 Mesh 修复救回来。

Mesh 化命令大致如下：

```bash
python render.py \
  -s data/bike_DJ_4 \
  -m output/<run_id> \
  --unbounded \
  --skip_train \
  --skip_test \
  --mesh_res 512 \
  --depth_trunc 1
```

这里有几个参数比较关键。

`--unbounded`：使用 unbounded mesh extraction。我的自行车是在室外拍摄的，背景和空间范围没有一个很干净的边界，所以 bounded 模式不太适合直接套。

`--skip_train` 和 `--skip_test`：跳过训练集和测试集视角渲染，只关注 Mesh 输出。后面如果要检查图像渲染质量，可以再单独打开。

`--mesh_res 512`：unbounded mesh extraction 的分辨率。官方示例里常见 `1024`，但我这里用 `1024` 会遇到内存压力（因为我的高斯球数量太多），最后降到了 `512`。这一步是很现实的取舍：分辨率更高不一定代表最后打印更好，因为中间还有减面、修补、加厚、切片等环节；如果机器先爆内存，后面就没有后面了。

`--depth_trunc`：我当时加了这个参数，具体数值没有完整记录，大概在 `1` 左右。这里不建议照抄数值，它和数据尺度、相机范围、场景大小都有关系。更稳的做法是先用较保守的参数跑通，再根据 Mesh 结果调整。

2DGS 的 `render.py` 在 Mesh 输出时会生成原始 Mesh 和 post-process 后的 Mesh。unbounded 模式下常见输出名类似：

```text
fuse_unbounded.ply
fuse_unbounded_post.ply
```

另外，2DGS 的 Mesh 颜色更接近顶点颜色这类结果，不是 SuGaR 那种传统 UV 贴图工作流。对我这次单色打印来说，这一点影响不大。颜色再漂亮，打印前真正要解决的还是几何。

## 爆内存、破面，以及数据采集的债

Mesh 化阶段最直接的坑是内存。

一开始我输入的高斯模型点比较多，Mesh 化时需要做体素化 / TSDF 相关处理，内存压力会迅速上来。参数看起来只是几个数字，实际背后是成倍增长的体素网格、采样点和中间张量。`mesh_res=1024` 看起来精细度很高，但实际运行时内存完全不足，我修改为512后可以满足条件，同时观察细节也基本够用。

如果是 bounded TSDF，`voxel_size` 会更直观地影响体素大小。体素越小，细节保留越多，内存压力也越大；体素越大，内存压力下降，但细结构可能被吃掉。自行车这种模型很尴尬，因为辐条和车架管都想要细节，但它们又正是最容易让重建和打印出问题的地方。

我的经验是：不要一上来就追最高分辨率。先跑出一个完整 Mesh，看它的主要结构是否成立，再逐步调高精度。否则很容易在“爆内存”和“跑出来一堆碎片”之间反复横跳。

3DGS 有时候会给人一种错觉：某个角度看起来挺好，好像模型就已经成了。但 Mesh 化以后，很多问题会露出来。

比如自行车某些部位在 3DGS viewer 里看着还行，转成 Mesh 后却出现破面。原因通常不是 Mesh extraction 单方面的问题，而是那一块本来就没有足够可靠的几何支撑。可能拍摄角度不够，可能某些细节长期被遮挡，也可能局部反光、运动模糊、背景混淆让 COLMAP 和后续训练都没有拿到稳定信息。

自行车尤其需要注意这些位置：

- 车轮内侧。
- 辐条交叉处。
- 车架管和连接点。
- 前叉、后叉这类细长结构。
- 车座、车把等容易被遮挡的部件。

如果目标只是做一个能看的 3DGS，少几个角度可能还可以靠视觉上的连续性糊过去；如果目标是打印，角度缺失就会变成洞、断面、粘连和奇怪薄片。

这也是我现在对采集数据的理解：**不要只拍好看的角度，要拍让后续几何重建放心的角度。**

## Mesh 修复：让模型真的能打印

2DGS 输出 Mesh 以后，还远远没到可以直接打印的程度。后面主要做了几类处理。

第一是减面。原始 Mesh 面数较高，直接丢给后续软件会比较吃力。减面需要控制尺度，不能把轮圈、车架这些结构直接减没，也不能让表面变成过于明显的低模折面。

第二是修补破面。自行车上很多局部结构都需要检查，尤其是细管连接处、轮圈边缘。这里不是简单点一个“自动修复”按钮就结束，很多地方需要手动判断到底应该补成什么形状。

第三是辐条重建。原始重建里的辐条非常容易断，也很容易细到无法打印。最后我对辐条单独进行了圆柱体建模，用更规则、更可控的几何替换不稳定的重建结果。对 3D 打印来说，这种“承认重建不适合某些细结构，然后用传统建模补上”的做法反而更靠谱。另外辐条因为太细，实际3D打印时很难实现，因此实际建模的半径要增大至2-5倍，同时减少数量。

第四是部分拓扑修复。目标不是把它修成工业 CAD，而是让切片软件能稳定识别，让打印工作室拿到以后不会被一堆非流形边、漂浮碎片和过薄结构折磨。

## 3D 打印与实物效果

Mesh 修到能打印以后，我把模型交给工作室打印。具体材料我这里没有记录。打印采用单色，整体比例大约是 `1:6`。关于比例，其实mesh建出来的时候也不是1:1的，这个大小我没有细琢磨原因，后续如果理解以后会修正。

打印前还做了一个很现实的修改：**加粗辐条半径**。在屏幕上看起来合理的细线，到了打印机那里可能就是不可靠结构。尤其是自行车辐条这种又细又长、还要在去支撑时承受外力的部件，实际应该需要单独打印的，但我实现的时候没有投入太多精力在工艺上，主要还是验证完整的技术链路。

最终打印耗时大约 **21 小时**。打印完成后模型上还有大量支架，需要手工去除。这个过程也会再次考验模型结构：如果细节太脆，去支撑时很容易把真正的模型一起掰掉（实际已经掰掉很多了，我的辐条！我的链条！）。

最后成品整体效果还可以。它不是一个完美的工业模型，但作为一次从 3DGS 到实体化的实验，我觉得已经把这条链路里最关键的几个问题暴露出来了：数据采集、Mesh 化、细结构修复、支撑和后处理，每一步都会影响最终手里的东西。

## 小结：这次实验得到的经验

**3DGS 适合做视觉表达。** 它能很快给出漂亮的新视角渲染结果，但漂亮不代表几何上适合制造。

**2DGS / SuGaR 这类方法是在帮 3DGS 靠近传统几何。** SuGaR 的 textured mesh 工作流对可视化和编辑很友好；2DGS 在我这次自行车数据上给出了更平整、更适合打印前处理的表面。

**3D 打印需要的是可制造模型。** 细结构要加厚，破面要修，拓扑要清理，支撑要考虑，比例也要让步。数字模型里能看见的东西，不一定能按原样打印出来。

如果下次再做类似项目，我会在拍摄阶段就为 Mesh 和打印服务，而不是只为 3DGS viewer 服务。尤其是自行车这种细结构多、遮挡多的物体，需要更系统地补足各个角度；对辐条这类结构，也可以一开始就计划采用“重建主体 + 手工规则建模补细节”的混合方案。

这次算是把高斯从屏幕里请了出来。过程不优雅，但最后桌上确实多了一辆小自行车。

---

## 一点我的思考

通过这次技术验证以及实际工作，我认为3DGS转mesh可行，但可能不是一个好的路径。毕竟3DGS算是引入了一种新的三维表征方式，它高效的渲染方式也是其创新之一，将3DGS转mesh似乎又走了回头路，可以在一定场景下作为替代方案，但真正接纳3DGS或许才是更好的选择。
